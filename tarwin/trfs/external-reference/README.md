# TRFS external-reference tests

## No independent format reference was found in the sources searched

TRFS v1 (`../TRFS.md`) is a new native format of this repository ("not an
interpretation of btrfs, FAT or an earlier TRFS format"). The search below
identified no independent specification, implementation or corpus. No test here
claims external conformance of the on-disk layout, records, anchors or
snapshots. What is missing for that: a second TRFS v1 implementation or an
independently produced image corpus, written by someone working only from a
published, versioned specification, with its own provenance.

Searched (Cairn `tessera`, snapshots 3816-3831):

- the full repository file index (19,773 paths) for trfs, filesystem,
  reference, corpus, vector, fixture, upstream, vendor, interop, conformance;
- `tessera-packages/tarwin/trfs` (spec, README, sources, tests, fixtures);
- `tessera-packages/tarwin/docs` (coverage, decisions), `TARWIN-CHANGES.md`,
  `tarwin/conformance`;
- `tessera-packages/tessera/roadmap` (Tarwin, TarwinHosted,
  05-storage-and-state, security) and every documented upstream source
  (`sysroot/*`, `build/app/UpstreamSource.kira`).

Found and rejected as references for TRFS: Debian `btrfs-progs_6.14-1`
(btrfs, a different filesystem), the Microsoft exFAT specification and
`mtools` (FAT/exFAT servers), ext4/btrfs performance baselines in
`tarwin/conformance`, and the QEMU measured-volume fixture (generated by this
repository from `TRFS.md`).

## What is tested against external references

TRFS.md fixes its encryption as standard XTS-AES-256 per 4096-byte sector,
tweak = sector index as a 128-bit little-endian integer, key = data key ||
tweak key (IEEE 1619). That part has independent authorities:

| Reference | Version | Provenance |
| --- | --- | --- |
| NIST CAVP XTSGenAES256, "data unit seq no" | CAVS 11.0, 2011-03-15 | [NIST XTS vectors](https://csrc.nist.gov/CSRC/media/Projects/Cryptographic-Algorithm-Validation-Program/documents/aes/XTSTestVectors.zip), ZIP SHA-256 `67bb04b018182f65530596786e7783f817d2e56509bf3b1f066609b8e3e29c36` |
| pyca/cryptography | 44.0.3, bundled OpenSSL 3.4.1 | PyPI, pinned in `run.sh` |
| LibreSSL `openssl enc -aes-256-xts` | 3.3.6 | `/usr/bin/openssl`, macOS 26 |

Positive:

- `XtsSector` reproduces all 600 whole-block NIST vectors, both directions;
  pyca and LibreSSL reproduce the same 600.
- A volume written through `TrfsEncryptedMedia` decrypts with pyca and with
  LibreSSL to the same bytes the plaintext writer produces.
- A plaintext TRFS image encrypted by pyca and by LibreSSL (identical
  outputs) mounts through `TrfsEncryptedMedia` and reads back a directory,
  a sparse file with an EOF fragment and a symlink.
- Only externally encrypted zero anchors format as blank.

Negative:

- Tweak + 1, byte-swapped tweak, swapped key halves, and a flipped
  ciphertext bit never reproduce a NIST vector.
- The mount-and-read check rejects a wrong tweak or key, swapped sectors, or a
  flipped ciphertext bit. Damage to file data can be detected at read rather
  than mount time: TRFS authenticates pages on demand, not through XTS alone.
- The 400 partial-block (ciphertext-stealing) vectors are outside the
  4096-byte data unit; `SectorPin` refuses partial-block units.

`tools/xts_ref.py check` re-reads the decrypted image from `TRFS.md` with
Python's hashlib as a cross-check of layout and hashing. It is a second
reading of our own spec, not an external reference.

## Running

    sh run.sh

Without `TRFS_XREF_PYTHON` (set by `run.sh`) the external-implementation
tests skip; they never pass silently.
